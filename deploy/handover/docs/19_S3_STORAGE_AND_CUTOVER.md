# Объектное хранение и переход с RWX

S3-профиль использует PostgreSQL для идентичности файлов и состояния публикации. Scanner artifacts, generated reports и Classic media находятся в приватном корпоративном bucket. В файловом профиле остаются `/app/aspm-private` и `/app/media`. Classic отчёты, формируемые по запросу, используют временные файлы. [Инвентаризация](STORAGE_INVENTORY.md)

## Чистая установка

1. Подготовьте приватный bucket и стабильный префикс. Запретите публичный доступ. Включите versioning, шифрование и аудит, если их поддерживает поставщик. Для незавершённых multipart uploads настройте AbortIncompleteMultipartUpload. Сроки retention, очистки старых версий и Object Lock утверждает владелец.
2. Создайте Secret с S3 access key и secret key. Для временных credentials заполните `sessionTokenKey`. При собственной CA создайте отдельный Secret с `ca.crt`. Для ротации обновите Secret и выполните контролируемый rolling restart использующих его deployment.
3. Добавьте [S3 overlay](../config/values-storage-s3.example.yaml) после основного профиля. Задайте HTTPS endpoint, bucket, префикс, адресацию и точные CIDR/port для NetworkPolicy. SigV4 и проверка TLS обязательны. Необязательное SSE используется только после проверки поддержки провайдером.
4. Runtime-учётной записи нужны `GetObject`, `GetObjectVersion`, `PutObject` и `AbortMultipartUpload` на выделенных префиксах. Для SSE-KMS дополнительно выделите необходимые права на конкретный ключ. Runtime не требует управления bucket, IAM или удаления версий. Выдайте отдельные права контролируемому backup/restore оператору и независимому backup storage.
5. Убедитесь, что рендер Helm сохраняет основной профиль HA, параметры PostgreSQL TLS, миграционный Job и тест HTTP. S3-профиль убирает PVC evidence и media. У внешнего PostgreSQL и Valkey остаются собственные механизмы персистентности. Dedicated Prometheus сохраняет отдельный PVC под TSDB/WAL. В `emptyDir` находятся временные parser, upload и export файлы, а также отдельные временные данные nginx и метрик.

Один небольшой служебный объект проверяет запись и чтение на старте. System Health и мониторинг читают probe с короткими таймаутами. Django readiness продолжает проверять PostgreSQL, брокер и cache, чтобы краткий сбой S3 не убирал рабочие страницы целиком. Запросы, которым нужен S3, получают ошибку 503. Временные сетевые ошибки у обработки ScanRun и generated report проходят до трёх повторов через outbox.

## Целостность и публикация

Для S3 используется условная запись If-None-Match при PUT и завершении multipart. После записи приложение читает сохранённую версию и сверяет полные размер и SHA-256. Для чтений закреплённой версии используется VersionId, если S3 его возвращает. До проверки bytes объект остаётся STAGED. В одной транзакции PostgreSQL приложение делает ссылку доступной и публикует outbox, либо фиксирует оба файла generated report как COMPLETED. Большие файлы передаются порциями. Для скачивания проверенный файл помещается на ограниченный локальный том до отправки заголовков. Обслуживание идёт через Product RBAC приложения с attachment, CSP и nosniff. У приложения нет публичных или presigned URL. [S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)

## Контролируемая миграция

- Сначала запустите `python manage.py aspm_storage_transfer plan` из контекста со старыми файловыми томами. План проверяет ссылки и хеши. Ограничьте доступ к выводу, который содержит логические имена файлов. Устраните пропавшие или повреждённые объекты до переключения.
- Подготовьте отдельный maintenance pod с образом кандидата, старыми приватными томами, S3 Secret и CA. Оставьте backend `filesystem`, но добавьте переменные целевого S3. Миграции приложения должны быть применены.
- Для финального прогона закройте входящий трафик, остановите Beat, дождитесь завершения активных worker и остановите web/worker. Остановите внешние задания и административные записи. Pending outbox остаётся в PostgreSQL. Сохраните копию БД по процедуре DR.
- Выполните `python manage.py aspm_storage_transfer copy --writers-paused`, затем `python manage.py aspm_storage_transfer verify --writers-paused`. Повтор после сбоя проверяет сохранённые S3 версии и продолжает с оставшихся записей. Команды не меняют ссылки ScanRun, report и Classic media.
- Переключите Helm на S3 при закрытом трафике. Проверьте старые сканы и отчёты, Classic вложения, новую загрузку, оба формата generated report, поиск и отказ при доступе из другого Product. После проверки откройте трафик. Сохраните RWX и исходный recovery point на весь rollback window.
- Пока в S3 не принимались новые записи, можно вернуться к старому профилю. После возобновления writes возврат требует согласованного восстановления или обратной синхронизации с проверкой новых записей. Переключение при активных writers создаёт расхождение данных.

`python manage.py aspm_storage_orphans --grace-hours 72` выдаёт dry-run аудит. С `--retire-staged --writers-paused` команда может пометить просроченные STAGED записи RETIRED. Физическое удаление выполняет оператор отдельной учётной записью по проверенному перечню точных VersionId после истечения срока хранения. Для READY записей подтвердите ссылки из всех продуктов и legacy media независимо. Повторите проверку непосредственно перед удалением. Недоступность PostgreSQL или S3 должна остановить очистку.

Сохраняйте прежний публичный hostname при переносе, если он записан в исторических immutable отчётах. Содержимое этих отчётов и встроенные ссылки сохраняются при копировании.
