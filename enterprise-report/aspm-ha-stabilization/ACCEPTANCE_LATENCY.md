# Задержка приёма сканов

В предыдущей квалификации 1 web / 1 worker → 2 / 3 дал 84,50 → 126,71 HTTP RPS и 2,98 → 3,83 завершённых ScanRun/с. 78,65 → 255,67 мс измерялось на клиенте. Тогда не было телеметрии отдельных этапов, поэтому точную атрибуцию исторической разницы установить невозможно.

Повтор использовал тот же изолированный PostgreSQL, небольшой синтетический JSON, 24 уникальные отправки по три параллельно, шесть читателей и 16 секунд непрерывных GET. Каждый запуск начинал с отдельных idempotency keys. Диагностический Django добавлял Server-Timing только на POST скана. Финальный образ собран обычным путём. Суммарные request/limit для A и B сопоставимы с погрешностью округления. Лимит Django был 2 CPU на одном pod в A и 1 CPU на каждом из двух в B. В C единственное изменение от B — 2 CPU на каждом Django, при тех же requests, ресурсах nginx, worker и памяти.

| Режим | GET 200 | Клиент p50, мс | API p50, мс | Django p50, мс | Остаток вне WSGI p50, мс |
|---|---:|---:|---:|---:|---:|

| B, 2/3, следующая отправка по готовности | 1647 | 120,43 | 54,81 | 72,46 | 54,12 |
| C, 2/3, следующая отправка по готовности | 1682 | 137,16 | 50,93 | 67,61 | 67,19 |
| A, 1/1, задано 75 GET/с | 1101 | 116,34 | 25,54 | 32,30 | 82,90 |
| B, 2/3, задано 75 GET/с | 1200 | 164,71 | 67,02 | 86,20 | 76,00 |
| C, 2/3, задано 75 GET/с | 1200 | 123,10 | 50,64 | 66,12 | 45,42 |

A при заданных 75 GET/с доставил 1101 из 1200. Для причинного сравнения B и C доставили все 1200 в обоих прогонах. Повышение только CPU limit одного Django с 1 до 2 CPU снизило медиану клиента на 25% и API на 24%. Сумма throttled periods веб-контейнеров упала с 28/368 до 11/366, а суммарный throttled time с 7,46 до 2,76 с. Отдельное сравнение с клиентами без заданной частоты показало throttled periods 25/373 → 6/367. Этот диагноз объясняет воспроизводимую долю ухудшения под нагрузкой. Полностью воспроизвести прежние 255,67 мс не удалось. В финальной лаборатории сохранены 2 CPU на Django. Для burst-нагрузки на внешнем кластере 2 CPU на Django — начальная настройка, подтверждённая этим сравнением.

Строки включают вложенные интервалы. Например, SQL rate limiter входит в Django и DB, а сохранение файла входит в транзакцию приёма. Сумма медиан не даёт медиану полного запроса. Время команды с явным lock включает обмен с БД и исполнение. UPSERT rate limiter может ожидать row lock, а приложению доступна только длительность всего UPSERT. Явные команды блокировки заняли менее 1 мс в медиане. Измерения не обосновывают изменение SQL, протокола fencing, transaction outbox, idempotency или работы с оригиналами.

Контролируемые прогоны A/B/C шли через ClusterIP. Остаток вне WSGI включает клиент, транспорт, nginx, постановку на выполнение и отправку ответа. Историческую задержку Traefik из этого остатка определить нельзя. Замер Loopback TLS на финальной сборке вынесен отдельно, исходные интервалы хранятся в журнале.

## TCP и TLS на финальном образе

В отдельном последовательном прогоне все 12 малых upload через Traefik TLS вернули 202. Медианы составили 0,23 мс на TCP connect, 6,05 мс на TLS handshake, 27,60 мс от готовности TLS до первого байта, 33,92 мс на весь запрос и 19,38 мс на handler API. Интервал после handshake включает upload, Traefik, nginx, Django и путь ответа. Эти измерения сделаны на Loopback при готовой топологии 2/3/1. Они не разлагают исторические сетевые задержки или задержки нагрузочных A/B/C. [Журнал транспорта](raw/acceptance-tls-transport.jsonl)
