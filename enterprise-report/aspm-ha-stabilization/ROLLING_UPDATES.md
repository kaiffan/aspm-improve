# Rolling update

## Исторические 13 отказов

Все 13 ошибок исходного прогона были `ConnectionRefusedError` на прямом ClusterIP, в двух интервалах 14:18:02,9–05,4 и 14:18:19,4–22,7 UTC. Отказы затронули API, страницы и CSS, который выдаётся nginx без Django. У исходного nginx была TCP readiness и отсутствовал preStop. Дальнейший кандидат уже использовал HTTP readiness на CSS и согласованный drain nginx/Django. Наиболее вероятна гонка shutdown nginx с обновлением маршрута Kubernetes Service при смене pod. Историческая запись не содержит EndpointSlice или IP для отказавших соединений, поэтому конкретный pod и точку маршрутизации установить невозможно. Тот прогон обходил Traefik и TLS. Последующие исторические прогоны дали 0/2358 и 0/1995 ошибок.

## Метод проверки

Каждый из повторов 5–7 — отдельный restart Deployment с финальным SHA и устойчивой топологией 2/3/1. По 175 с трафика, по два TLS-клиента без повторов, два TLS-клиента с лимитом в три попытки и два прямых клиента ClusterIP. TLS проверял лабораторный CA. Список маршрутов, интервалы и политика повторов одинаковые. Клиенты аутентифицировались перед началом и продолжали с той же сессией. Ресурсы CSS проверялись по SHA-256. Параллельная передача 48 МиБ использовала второй port-forward к тому же Traefik. В первом из этих трёх прогонов пауза между чанками 30 мс, в двух последующих 100 мс, чтобы передача продолжалась после смены EndpointSlice.

EndpointSlice опрашивался каждые 0,7–1 с. Уходящий endpoint сначала наблюдался с `ready=false, serving=true, terminating=true`, затем переставал обслуживать и исчезал. Новый endpoint становился Ready после startup/readiness. Nginx имеет проверку CSS, preStop 5 с и SIGQUIT, `worker_shutdown_timeout=120s`. Django имеет preStop 130 с. Pod grace period 150 с оставляет время на оба этапа. В ходе прогонов запросы стартовали через Traefik и ClusterIP, а не маршрутизировались к заранее выбранному pod. Трасса показывает непрерывность обслуживания и существование draining endpoints, но не идентифицирует конкретный upstream pod для загрузки каждого запроса.

В прогоне 1 одновременно восстанавливалось масштабирование с 1/1. Один прямой запрос ClusterIP завершился `TimeoutError`. В прогонах 1–3 отдельный запрос оригинала вернул 404. После замены учётных данных на токен владельца скачивание прошло предварительную проверку с ожидаемым SHA. В прогоне 4 передача 48 МиБ и TLS наблюдатели использовали один port-forward. Шесть запросов без повторов и два с повторами окончательно завершились тайм-аутом в пределах интервала загрузки, первые ошибки начались до старта Helm upgrade. Все 1526 прямых запросов ClusterIP прошли. Повтор с отдельным port-forward к тому же Traefik устранил обнаруженное взаимное влияние. Эти наблюдения локализуют текущие тайм-ауты в общей цепочке лабораторного туннеля. Они не объясняют исторические отказы прямого ClusterIP.
