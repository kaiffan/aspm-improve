# DefectDojo API performance audit

### Environment

DefectDojo Open Source 3.5.100, PostgreSQL 18.6, Django 5.2.17, macOS 26.6.1 на Apple M5 с 16 ГиБ RAM. Нагрузочная БД содержала ровно 1 000 000 синтетических findings до и после испытаний. Релизная основа стенда — `334bef02d65a74909fe976b22724526474d5a0f6`. Патч подготовлен на отдельной ветке `codex/api-v2-findings-performance` от `origin/dev` (`71ba3f0e1b`) и собран поверх того же runtime 3.5.100. [Окружение и происхождение сборок](environment.md).

### Existing optimizations

- Prefetch vulnerability references сохранил 24 SQL-запроса на страницу из 100 findings и один запрос к таблице ссылок. В изолированных тестах list и detail вернули обе связанные записи в исходном порядке и JSON-формате.
- `fast_offset=1` остался opt-in. На OFFSET 500 000 исходный стандартный план занял 362 мс, а узкий индексный проход существующего FAST — 27 мс. FAST сохраняет точный count и возвращает тот же набор данных. SQL и тесты подтвердили переход на стандартную пагинацию для сортировки `-id`.

### Newly discovered bottlenecks

`GET /api/v2/products/` выполнял коррелированный подсчёт активных findings при подсчёте продуктов и при выборке страницы. Каждый план повторял подзапрос 13 раз. Сериализатор затем выполнял ещё 13 SELECT для списков ID. У крупнейшего продукта 532 569 ID и внешний sort на 6 272 КиБ. [Рейтинг кандидатов и профиль сериализации](bottlenecks.md).

### Implemented changes

После авторизации, фильтрации и пагинации PostgreSQL одним запросом группирует активные finding ID по продуктам страницы. Каждый массив упорядочен по ID. Его длина используется для точного `findings_count`. Точный count продуктов и `DISTINCT` по-прежнему вычисляет штатный пагинатор. Оптимизация ограничена действием `list`, поэтому `delete_preview` получает прежнюю пагинацию. [Изменённые файлы](changed_files.md), [патч](product-findings.patch).

После добавления ограничения `list` повтор на итоговом образе дал p95 1109.7 и 1982.6 мс соответственно, по 50 запросов с прогревом. Дополнительный фильтр по продукту с 28 143 ID после повторного прогона из 50 запросов дал p95 262.6 → 125.9 мс при c=1. Первичная серия из восьми запросов содержала выброс и сохранена в сырых данных.

Суммарное SQL-время products в диагностическом запросе сократилось с 5 410 до 889 мс. До патча два плана с коррелированным count заняли 1 939 и 1 749 мс и прочитали примерно по 694 тыс. shared blocks. После патча один `GroupAggregate` занял 830 мс с 111 442 shared reads и внешней сортировкой на 14 872 КиБ. Эти значения относятся к отдельным `EXPLAIN ANALYZE`, а не к HTTP p95. [Исходный SQL](baseline_sql.md), [SQL после патча](after_sql.md).

HTTP 200 получен во всех измеренных запросах. Совпали полные SHA-256 контрольных ответов для 16 из 16 пар маршрут/concurrency, включая размер, порядок, точный count и все поля. Products сохранил 13 результатов, 840 282 ID активных findings и тело 5 798 301 байт. Разброс latency контрольных маршрутов не интерпретировался как эффект патча. [Исходные метрики и p50](baseline.json), [метрики после и повтор итоговой сборки](after.json).

В наблюдаемых снимках Docker память исходного uWSGI достигала 2.05 ГиБ, uWSGI с оптимизацией — 1.83 ГиБ, PostgreSQL — 312 МиБ. CPU PostgreSQL достигал 458% при выборочном опросе. Эти снимки включают разные фазы прогрева и нагрузки. [Снимки Docker stats](resources.txt).

### Regression tests

43 теста прошли, 5 штатно пропущены. Проверены пагинация, сортировки и фильтрация, запрет доступа к чужим данным, два vulnerability ID в обеих ветках представления и существующий FAST OFFSET. Полные HTTP-ответы сравнены на восьми маршрутах и комбинациях фильтров. OpenAPI совпал побайтно. [Подробные результаты тестов](test_results.md).

### Scalability assessment

При 10–20 млн findings список products всё ещё должен прочитать, отсортировать и сериализовать каждый активный ID для продуктов на странице. Размер страницы по продуктам слабо ограничивает объём ответа, если один продукт содержит сотни тысяч findings. Параллельные запросы увеличивают давление на CPU, временные файлы PostgreSQL и память uWSGI.

Точный count findings остаётся линейным по числу подходящих строк. Стандартный глубокий OFFSET проходит записи до смещения, а FAST зависит от фильтра и сортировки. Покрытие замеров ограничено одним миллионом синтетических строк и concurrency 1 и 5. Данные и конкуренция production могут дать другой профиль.

### Rollback

В worktree патча выполните `git apply -R --check <путь>/product-findings.patch`, затем `git apply -R <путь>/product-findings.patch`. Патч меняет только код и тесты. Рабочий API на порту 8080 продолжает использовать исходный образ. Для остановки отдельного A/B стенда достаточно остановить контейнеры `django-defectdojo-nginx-perf-1` и `django-defectdojo-uwsgi-perf-1`. PostgreSQL-том остаётся на месте.
