## Окружение

Форк `kaiffan/aspm-improve`, локальная ветка `codex/api-v2-performance-round2` от `origin/dev` (`71ba3f0e1b`). В этой ветке отдельно применён патч Product первого раунда. Изменённые исходные файлы сверены с релизом 3.5.100. Тестируемая сборка наследует проверенный runtime 3.5.100 первого раунда, а Dockerfile заменяет только три Python-файла. SHA-256 обоих существующих исправлений Findings совпали в контейнерах. Основной порт 8080 продолжает обслуживать исходный образ. [Идентификаторы образов](round2/images.txt).

Основные A/B тесты выполнялись на том же PostgreSQL 18.6 с 1 000 000 findings. MacBook Air M5, 16 ГиБ RAM, OrbStack, 10 логических CPU. Обе сборки принимали запросы через один URL на порту 48081. Пары по 25 измерений чередовались в двух раундах с 5 запросами прогрева на каждую серию.

## Исправления и SQL

1. **Полный Product detail дважды читал findings.** Коррелированный count и отдельный запрос за списком заняли 816 и 911 мс в `EXPLAIN ANALYZE`. Каждый прочитал около 423 тыс. shared blocks. Теперь detail использует уже существующий для списка пакетный `ArrayAgg` после проверки доступа, а count выводится из длины массива. Один план занял 934 мс и прочитал 422 808 shared blocks. Число SQL-запросов осталось 9, поскольку count до патча был частью запроса Product. Суммарное SQL-время диагностического запроса снизилось с 1897 до 933 мс.
2. **Пользователи Product summary получали весь массив ID.** Новые opt-in режимы `?findings=count` и `?findings=none` работают на list и detail. `count` возвращает точный `findings_count` без `findings_list`. Один `COUNT(*) GROUP BY product_id` использует имеющийся индекс по `test_id, active`. Измеренный index-only план на 532 569 строках занял 48 мс и прочитал 12 926 shared blocks из кеша при 13 900 heap fetches. `none` опускает оба поля и в измеренном запросе выполняет 0 SQL к findings. Стандартный режим `full` сохраняет оба поля, точный count продуктов и прежний порядок.
3. **Tests с Jira issues выполняли два дополнительных SELECT на группу.** Для 1, 20 и 100 связанных issues регрессия зафиксировала 13, 51 и 211 запросов для списка и 12, 50 и 210 для detail. Теперь prefetch загружает Jira Project и Jira Instance вместе со страницей в двух пакетных запросах. Полный JSON, включая URL issue и группы без ссылки, сохранён.

[SQL и EXPLAIN до](round2/baseline_sql.md) · [SQL и EXPLAIN после](round2/after_sql.md) · [Jira до](round2/fixture_before_sql.md) · [Jira после](round2/fixture_after_sql.md)

В форке не найден клиент, который явно извлекает `findings_list` из ответа Product API. Asset API публикует аналогичное поле, а Product Export намеренно исключает его. Исходники не дают сведений о внешних потребителях, поэтому полное поле остаётся в стандартном контракте.

## Ограничения и откат

При 10–20 млн findings полный ответ остаётся пропорционален числу активных ID выбранных продуктов и может упираться в память uWSGI и временные файлы PostgreSQL. Точный count остаётся пропорционален числу подходящих индексных записей. У Findings по Product точный count в профильном плане занял 47–68 мс, а существующий FAST при глубоком фильтрованном OFFSET всё ещё проходил сотни тысяч записей. У Tests стоимость JSON зависит от числа вложенных групп. Измеренный предел нагрузки — c=10, на 15–25 параллельных запросов результатов пока нет.

Откат в worktree форка — `git apply -R --check /путь/к/round2.patch`, затем `git apply -R /путь/к/round2.patch`. Патч первого раунда остаётся в индексе worktree. Изменений схемы и индексов нет. Остановка Compose-сервисов проекта `dd35100-round2` отключает только отдельную A/B сборку и оставляет исходный API и его том PostgreSQL на месте.
