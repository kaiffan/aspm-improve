# Коррекция измерения RSS

В унаследованном из Round 4 `worker_rss.py` из списка исключались PID, являющиеся родителями других uwsgi-процессов. В данном runtime PID 1 сам является `uWSGIWorker1Cor`, а служебный logger имеет procname `uwsgi`. Поэтому прежний sampler пропускал первый worker и включал logger. Сохранённые primary HTTP/SQL timings и Docker CPU/whole-container memory от этого не зависели: они собирались другими механизмами.

Raw значения не переписаны. В сводках старый worker RSS — только нижняя граница максимума наблюдённых дочерних процессов, не peak всех четырёх workers. Нельзя использовать его для строгого процента снижения памяти. Исправленный sampler выбирает все `uWSGIWorker*`, включает PID 1, сохраняет PID→RSS и scope в каждой записи. Полный парный c25 контроль Round4/Round5 находится в `raw/diagnostic-pair-*-rss.jsonl` и отдельно показан в RESULTS. Интервал 0.4 s означает sampled peak, не непрерывный максимум.

Часть последующих standalone серий уже использовала исправленный sampler. Поле `worker_rss_scope` отмечает scope сводки; при смешанном/старом scope результат также считается нижней границей. Для сравнения общей памяти приложения доступны независимые Docker working-set samples (`web_container_memory_peak_mib`), которые не равны сумме RSS процессов с разделяемыми страницами. Исторический отчёт Round 4 сохранён; эта заметка уточняет его memory measurement limitation.
